# 限流器实现
实现一个限流器，需要一下功能：
- 能指定限流器算法
- 能指定限流器限流值
- 能具体到接口维度的限流器配置
- 能切换限流器算法
- 能修改限流值
# 实现思路
- 提供限流器抽象类，实现限流器基本功能，修改值，初始化、限流判断 
- 提供限流器工厂，根据不同枚举创建不同限流器实例 
- 实现限流器管理类，
  - 使用一个map管理限流器和接口路径的映射关系
  - 提供接口绑定、重新绑定功能
  - 提供根据接口路径判断限流
# 限流器实现
## 滑动窗口限流器
 滑动窗口限流器需要指定窗口大小，桶的数量，尤其要注意环形数组中，桶id的设计思维，和环形数组下标设计思维
- 桶的id使用当前时间戳除以桶大小，从而把桶大小的一段时间都计算成一个id，其实就是当前时间戳是桶大小的几倍
- 桶的id再和窗口的桶数量取模，就可以计算出来桶在窗口的位置
- 有效桶永远是最近的窗口桶数量，也就是最早的一个有效桶是当前桶id-桶数量+1，注意不能直接加环形数组的请求总和
  因为有的位置的桶有可能都是很早之前的（环形数组是重复利用的）
## 令牌桶
是基于时间的一个计算。

我们可以把“时间窗口”理解为桶的大小。在时间窗口内，我们允许通过的请求数量，就可以理解为桶内的令牌数量。

然后，用令牌数量除以时间，我们就可以计算出系统发放令牌的速度。我们要记录上一次发放令牌的时间。在请求到来的时候，用当前时间与上一次发放令牌的时间对比，根据时间差来补充令牌——也就是说，补充令牌的动作是在请求到达后按需触发的，以秒为单位。

具体逻辑如下：

1. 计算新增令牌：发多少令牌取决于当前时间与上一次时间的差值，乘以发令牌的速率。如果两个请求在同一秒内到达，时间差为 0，则不发放。
2. 更新桶内令牌：将新增的令牌数与当前桶内剩余的令牌数相加，并与桶的最大容量对比取较小值（不能超过桶的最大容量）。
3. 处理请求：判断桶内是否有可用令牌。如果没有，则直接拒绝；如果有，则令牌数减一并放行。这道题有个非常关键的点，一定要跟面试官确认：令牌桶允不允许预支令牌？

如果允许预支令牌，需要确认以下细节：

1. 允许预支几秒的令牌？
2. 如果允许预支，那么在请求过来且没有令牌时，我们就要往外预支。预支也就是说，要把发令牌的时间往后推。比如如果预支 3 秒，就将发令牌的时间更新为往后推 3 秒，然后给它发 3 秒的令牌数量。预支逻辑一定要注意发令牌的数量。

这里不是用发令牌的最近时间，而一定要是“上次发令牌的时间”加上“预支的时间”，然后再跟当前时间对比，看看是不是超过 3 秒了（因为不能让它无限地预支）。如果上一次预支了，那上次发令牌的时间就有可能比当前时间还要晚。这种情况我们还会让他预支吗？这个也要跟面试官确认。

就好比说：当前时间没有令牌，我让他预支了 3 秒；过了一秒又来了一个请求，这时候 token 又用完了，那这时候允不允许他在原来的基础上，再往后多发 1 秒的 token？因为他预支了 3 秒，现在过了一秒，还有一秒的窗口期
